# Step 3c - Spark performance tuning: partitions x persistence

Generated by `src/reporting/analyze_performance.py` from `results/tuning/runs.jsonl`; nothing is typed by hand.

Workload (`bigdata_pipeline/spark_tuning/TuningExperiment.scala`): `weather_cleaned` (303.6 M rows) broadcast-joined with `us_stations`, `repartition(P, state)`, optionally persisted, then three queries that reuse it (state x year x element mean; distinct stations per state x year; state x month mean TMAX). One warm-up iteration + 3 measured repeats per configuration, each configuration in a fresh JVM (`local[*]`, 24 cores, driver 3 GB). AQE is off in the grid so it cannot override P; the last row is Spark's defaults (AQE on, 200 partitions) for reference.

* Measured repeats: 25
* Fastest grid configuration: **p384-none** (325.79 s median)
* Speed-up from persistence at each partition count (none / persisted): {'8': 0.37, '96': 0.48, '384': 0.46}
* Caching break-even (materialisation time / average time saved per reusing query): P=8: each query is 52.3 s slower on the cache (too few partitions to read it in parallel) -> never pays off; P=96: saves 14.9 s per query, costs 423.11 s to build -> pays off after ~28.4 queries; P=384: saves 24.3 s per query, costs 446.48 s to build -> pays off after ~18.4 queries

Setup notes: shuffle and spill go to `spark.local.dir` on a Windows bind mount (`.spark-local`), because writing them inside the Docker VHDX grew the disk until WSL crashed (first attempt, archived as `results/tuning/archive_v1_runs.jsonl`). Host I/O therefore inflates absolute times for every configuration equally; comparisons between configurations remain fair. In the archived attempt p8-memory_and_disk failed with `SparkOutOfMemoryError` while it passed here: caching 303.6 M rows in a 3 GB heap is at the edge of feasibility.
